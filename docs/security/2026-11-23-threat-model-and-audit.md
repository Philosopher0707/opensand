# OpenSand threat model & security audit — 2026-11-23

Scope: `origin/main` at the time of this audit (worktree base SHA `0b295506da2468905e0a915b172807f2bf992731`), read-only. No product code was changed. PoCs ran against extracted/inlined copies of real source functions or against local files only; nothing touched the owner's `~/.opensand`, real chats, or real keys. Severity uses CVSS-style bands (Critical/High/Medium/Low) plus plain words.

## 1. Attack surface map

| Surface | Entry point | Who can reach it | Primary control |
| --- | --- | --- | --- |
| Local HTTP API | `packages/desktop/src/desktop-server.ts` `http.createServer`, binds `127.0.0.1` only (`this.host = options.host \|\| '127.0.0.1'`, `desktop-server.ts:76`) | Any local process/user on the same machine; a page open in any browser if the user visits it while OpenSand runs | Bearer/`X-OpenSand-Token`/`opensand_token` cookie, Host-header pinning, Origin allow-list, CSP (`desktop-server.ts:146-336`) |
| Webhook ingress | `POST /api/webhooks/:name` | Any local process (bypasses the main token check) | Per-IP rate limit + optional per-webhook HMAC/token secret (`webhook-gateway.ts:137-144`) — **secret is optional** |
| Electron IPC/preload | `packages/desktop/src/preload.cts`, `main.ts` | The renderer only (sandboxed, `contextIsolation:true`, `nodeIntegration:false`, `sandbox:true`) | `contextBridge.exposeInMainWorld('opensand', …)`, fixed IPC channel allow-list |
| CLI | `packages/cli/src/cli-app.ts` | Local shell user | Own `onApprovalRequired` callback into the shared `AgentCoordinator` |
| Local-exec daemon | `packages/local-exec-daemon/src/*` | The coordinator process (IPC/stdio, not network) | `bash-validator.ts` denylist (hard throw), OS sandbox (`sandbox-exec` macOS / `bubblewrap` Linux) when a profile is requested |
| MCP client/manager | `packages/coordinator/src/mcp-client.ts`, `mcp-manager.ts` | Configured MCP servers (child processes the user configured) | Tool output wrapped with `wrapUntrusted`/`escapeUntrustedText`; no declared `effect` ⇒ treated as `unknown`, which `autoAllows()` never auto-grants |
| External-engine wrapper (design, not yet shipped) | `docs/design/external-engines.md` | Local `claude`/`codex`/`copilot`/`opencode`/`codebuddy` CLIs the user already signed into | Documented to route every tool call through the same `ipc-bridge.ts:requestUserApproval`/`onApprovalRequired`, never emitting bypass flags (`--dangerously-skip-permissions` etc.) |

**Good controls already in place** (verified by reading, not just assumed):
- Electron: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` (`packages/desktop/src/main.ts:216-219`); external navigation is denied and redirected to the OS browser (`main.ts:224-234`); preload exposes a small, fixed set of IPC channels only (`preload.cts:24-69`).
- HTTP API: Host-header pinned to `127.0.0.1`/`localhost` (DNS-rebinding defense, `desktop-server.ts:301-312`), Origin checked and CORS reflected only for localhost (`desktop-server.ts:314-336`), token compared with `crypto.timingSafeEqual` over a SHA-256 digest (`desktop-server.ts:146-153`), session cookie is `HttpOnly; SameSite=Strict` (`desktop-server.ts:352`), token file written `0o600` (`desktop-server.ts:110`), request/header/keep-alive timeouts set against slowloris (`desktop-server.ts:228-230`).
- Workspace-file reads resolve symlinks with `realpathSync` and verify containment with `path.relative` before touching the filesystem (`packages/desktop/src/workspace-file-read.ts:11-14,31,41`), so traversal and symlink escapes are refused. Static renderer files (`desktop-server.ts:1577-1584`) only check `path.resolve(...).startsWith(rendererDir)`: traversal is refused, but symlinks are not resolved (see F7). (Cite corrected 2026-11-23 after Rigel's check.)
- Secrets: `VaultStore` master key file is `0o600` (`packages/coordinator/src/vault-store.ts:153,244`); no secret value was found concatenated into a `console.log`/`console.warn` call anywhere in `packages/*/src`.
- Supply chain: no `postinstall`/`preinstall` scripts in any `package.json` in the tree; no vendored-code directory exists in this repo (the PIN-file/parity-gate pattern referenced in other projects' notes does not apply here — `docs/design/external-engines.md` §3.2 describes a *future* PIN file for the wrapper script, not yet landed).

## 2. Findings

| id | area | finding | severity | evidence | reproduced / read | fix | gate/test to add | size |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| F1 | Approval (Electron desktop) | In **auto** approval mode, `requestUserApproval()` returns `true` as soon as `autoAllows(mode, req)` matches — **before** the "Safety Ceiling" dangerous-command check ever runs. `autoAllows()` itself has no awareness of command content: for `effect: 'shell_outside'` (unsandboxed shell) it returns `true` unconditionally unless the session is already tainted. So a destructive, fully unsandboxed command (`rm -rf /`, etc.) auto-approves with **zero** prompt in auto mode — directly contradicting the code's own comment ("Destructive shell commands … must never auto-approve") and the external-engine design doc's own approval table, which specifies `shell_outside` must **always** prompt, in every mode. | **Critical** | `packages/desktop/src/ipc-bridge.ts:798-814` (autoAllows checked/returned at 799-801; dangerous-pattern `mustPrompt` logic at 805-814 is unreachable once that return fires); `packages/shared/src/approval.ts:70-80` (`autoAllows`); contradicted by `docs/design/external-engines.md:250-251` | **Reproduced** — ran the verbatim exported `autoAllows()` logic (copied, not modified) with `mode:'auto', effect:'shell_outside'`: returns `true` regardless of the command. See PoC transcript below. | Evaluate the dangerous-pattern (`validateBashCommand`), `PolicyEngine.REQUIRE_APPROVAL`, and persistent-write checks **before** the `autoAllows()` early return, or have `autoAllows()` itself refuse `shell_outside` whenever `validateBashCommand(args.command).isDangerous` — matching the design doc's table. | Unit test in `packages/desktop/test/ipc-bridge.test.ts`: `requestUserApproval('exec_command', {command:'rm -rf /', unsandboxed:true}, …)` under `mode:'auto'` must return `false`/raise a prompt, not auto-approve. Add to CI. | S |
| F2 | Approval (shared coordinator, used by CLI + Desktop + future external engines) | `AgentCoordinator.runTurn()`'s `exec_command` fast path decides `needsApproval` using **only** the literal command string via `isStandingExecAllowed(gates.standingGrants, cmd)`. The match key is `{tool:"exec_command", command}` — it does not include `args.unsandboxed` or the requested `sandboxProfile`. A standing "always allow" grant a user approved for a command under sandboxed semantics therefore also authorizes the **same command text with `unsandboxed:true` appended**, with no new prompt, because `isAllowlisted` alone satisfies the gate at `coordinator.ts:447`. Separately, the "tainted shell after web content" check (it forces a prompt) that exists in `ipc-bridge.ts` (`this.tainted`, checked at line 785) is **never referenced in `coordinator.ts`** — a repo-wide grep for `tainted`/`taint` in `packages/coordinator/src` and `packages/shared/src` returns nothing. Since `onApprovalRequired` is only invoked when `needsApproval` is true (`coordinator.ts:462`), the standing-grant fast path skips the callback entirely — so even the Desktop app's own taint check in `requestUserApproval` never gets a chance to run for this case, because the call never reaches it. Net effect: once any standing grant exists for a command, a prompt-injected tool result or web page can get the model to replay that exact command **unsandboxed**, in a tainted session, with no fresh approval anywhere in the stack. | **High** | `packages/coordinator/src/coordinator.ts:436-500` (no `tainted` field anywhere in file); `packages/shared/src/standing-exec.ts:34-42` (`isStandingExecAllowed` signature takes `command: string`, not full args); `packages/local-exec-daemon/src/tool-registry.ts:103` (`unsandboxed` toggles `effect` but isn't part of the grant key); `packages/local-exec-daemon/src/command-runner.ts:78-86` ("Sandbox is opt-in via `input.sandboxProfile` … once requested it is never dropped" — i.e. the *default* spawn is unsandboxed unless a profile is explicitly requested) | **Read in code** — traced the full call graph (`coordinator.ts` → `standing-exec.ts` → `tool-registry.ts` → `command-runner.ts`); did not stand up a live daemon+coordinator integration harness to fire an end-to-end exploit, given the time budget for this pass. Recommend an integration test (see gate column) to convert this to "reproduced." | Make the standing-grant match key include `unsandboxed`/`sandboxProfile` (a grant approved under sandboxed semantics must not satisfy an unsandboxed request), and move taint-tracking out of `ipc-bridge.ts` into `coordinator.ts` so every front-end (CLI, Desktop, future external-engine wrapper) shares one taint check, consulted whenever `needsApproval` is computed — not just inside one caller's own `onApprovalRequired`. | Integration test: register a standing grant for `ls` (sandboxed), simulate a turn that read untrusted web content (`wrapUntrusted`), then call `exec_command({command:'ls', unsandboxed:true})`; assert it is rejected or re-prompted, not silently allowed. | M |
| F3 | Local-exec daemon (mode-independent backstop) | `bash-validator.ts`'s `DANGEROUS_PATTERNS` denylist is the **only** check that fires unconditionally regardless of approval mode or standing grants (`command-runner.ts:14-19` throws `SafetyGateError` before any spawn). It is trivially bypassed by quoting or indirection: `rm -rf "/"` does not match (the regex requires a bare `/` right after whitespace, not inside quotes), nor does `X=/; rm -rf $X` or driving the deletion through an interpreter instead of `rm`. Because F1 and F2 above show the approval layer can be bypassed, this denylist is sometimes the *last* line of defense for exactly the destructive commands it names, and it is easy to evade. | **Medium** | `packages/local-exec-daemon/src/bash-validator.ts:14-23` | **Reproduced** — ran the verbatim regex from line 16 against `rm -rf "/"`, `rm -rf ~`, `X=/; rm -rf $X`, `rm -rf /*`: the quoted and variable forms return `false` (no match) while the bare forms return `true`. | Treat this denylist as defense-in-depth only, not the safety boundary — the real boundary should be the OS sandbox (`sandbox-exec`/`bubblewrap`) being **mandatory**, not opt-in via `sandboxProfile`. Short term, normalize obvious quoting before matching and add a few of the bypasses as explicit patterns. | Add the four bypass strings above as regression cases in `packages/local-exec-daemon/test/bash-validator.test.ts`, asserting `isDangerous: true` (or that they're caught some other way) rather than silently passing as safe. | S |
| F4 | Local HTTP API / webhook ingress | `POST /api/webhooks/:name` is explicitly exempted from the main session-token check (`isWebhookIngress` at `desktop-server.ts:347` is one of the three bypass conditions at line 355). ### F1 PoC transcript (extracted-function reproduction, no files touched)

```
$ node -e "
const EFFECTS = { shell:1, shell_outside:1, read:1, edit:1, delegate:1, engine_run:1, network:1, browser:1, memory:1, external:1, vcs:1, control:1, spend:1, self:1 };
const NEVER_AUTO = new Set(['control','spend','self']);
const AUTO_EDIT = new Set(['read','edit','shell','delegate']);
const SHELLS = new Set(['shell','shell_outside']);
function autoAllows(mode, req={}) {               // verbatim from packages/shared/src/approval.ts:70-80
  if (mode !== 'auto_edit' && mode !== 'auto') return false;
  const effect = req.effect;
  if (!effect || !EFFECTS[effect] || NEVER_AUTO.has(effect)) return false;
  if (req.note && SHELLS.has(effect)) return false;
  if (effect === 'engine_run') return mode === 'auto' || req.sandboxed === true;
  if (mode === 'auto_edit') return AUTO_EDIT.has(effect);
  return true;
}
console.log(autoAllows('auto', { effect: 'shell_outside', args: { command: 'rm -rf /', unsandboxed: true } }));
```

## 3. Not found / out of scope this pass

- Did not stand up a live `desktop-server.ts` instance or a live `local-exec-daemon`, so F2 and F4 are "read in code," not end-to-end exploited. Recommend Dex or Rigel add the integration tests named above and flip them to "reproduced."
- MCP tool calls were traced only as far as confirming they have no declared `effect` (so `autoAllows()` never auto-grants them, `effectOf()` falls back to `"unknown"`) — did not audit individual MCP server implementations or the MCP transport (`mcp-client.ts` spawns a child process per configured server; command/arg validation on that config was not reviewed this pass).
- `docs/design/external-engines.md` is a design document for unshipped code; findings here are about the **current** native tool loop, which the design doc explicitly must sit beside without inheriting its risks (it says it never emits bypass flags and routes everything through the Desktop's own approval callback) — but F2 shows that very callback can already be skipped by the standing-grant fast path, so the external-engine wrapper would inherit F2 unless F2 is fixed first.
- Supply-chain `pnpm audit` was not run against the live dependency tree in this pass (read-only review of CI config only); recommend running it once as part of landing F5's gate.

## 4. Three gates to add first

1. **F1 regression test** (`packages/desktop/test/ipc-bridge.test.ts`): `requestUserApproval` must never auto-approve a `shell_outside`/dangerous-pattern command, in any mode. Smallest change, highest-severity finding.
2. **F2 integration test**: a tainted-session, standing-grant-allowlisted, `unsandboxed:true` `exec_command` call must be rejected or re-prompted by `AgentCoordinator.runTurn()` itself, not just by one front-end's callback.
3. **CI `pnpm audit` + secret scan** (F5): needs the owner's go-ahead to touch `.github/workflows/ci.yml`, but it is the cheapest, broadest-covering gate missing today — zero dependency/secret-leak coverage currently exists.
