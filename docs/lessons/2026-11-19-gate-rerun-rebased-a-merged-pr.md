# Re-running the gate on a merged PR rebased and force-pushed the merged branch

- **Trap:** After PR #143 merged, a second `scripts/pr-gate.sh --when-green 143` run rebased `job/worktree-guards` onto main, force-pushed it and exited `1`. The merge was done; the branch had no reason to move, and a force-push to a merged PR can rewrite history a reviewer already read.
- **Root Cause:** The gate checked the PR's state (`OPEN`, draft, mergeable) only in check 1, *after* the `--when-green` block that rebases and pushes. On a merged PR the base was naturally behind main, so the rebase path ran before anything noticed the PR was finished. Exit `1` also misreported a finished job as a failure.
- **Rule:** A tool that mutates a remote resource reads that resource's terminal state before its first mutating step, not after. `pr-gate.sh` now asks `gh pr view <PR> --json state,mergeCommit` first: on `MERGED` it prints `PR #<n> already merged as <sha>`, runs only the post-merge main CI check (exit `0` green, `4` red, `3` pending) and never fetches, rebases, tags or pushes. Re-running a gate must be idempotent, and the selftest must assert the absence of every mutating git call, not just the exit code.
