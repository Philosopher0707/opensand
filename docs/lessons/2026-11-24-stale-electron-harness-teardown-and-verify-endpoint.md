# Stale Electron harnesses cause ENOTEMPTY teardown races; a stub endpoint must never reach verify.sh

**Trap:** Two `verify.sh` failures on #248's rebased branch were `ENOTEMPTY: directory not empty, rmdir` in `account-shortcuts-real-window` and `dead-actions-real-window`. Both tests passed on their own. Separately, I had exported the stub `OPENSAND_ENDPOINT` (used to point engine-detection tests at a fake local server) into the shell that ran `verify.sh`, so the full suite was talking to the stub instead of the real local daemon.

**Root Cause:** (observed) Left-over Electron harnesses from earlier bot runs on the same Mac were still alive when the two real-window tests tore down their temp homes; a late child process recreated a directory under the home just as `rmdir` walked it, producing `ENOTEMPTY`. CI starts from clean runners, where those processes do not exist, so the failures were host-local rather than branch defects. The endpoint mistake was a scope error: the stub belongs only to the detection test that needs it, not to the environment of the whole verification script.

**Rule:** Before treating a real-window `ENOTEMPTY` teardown as a failure, check for stale Electron processes on this host (`ps`/`pgrep` for the harness) and rerun the single named test in isolation; do not rerun unchanged `verify.sh` three times or let a shared-host race block a push that CI decides. Keep the stub `OPENSAND_ENDPOINT` scoped to the single test command that uses it — never export it into a shell that also runs `scripts/verify.sh`. [observed: `account-shortcuts-real-window` and `dead-actions-real-window` each pass in isolation; CI on clean runners is authoritative]
