# Auto mode auto-approved unsandboxed and destructive shell before the safety checks

**Trap:** In `mode:'auto'`, `requestUserApproval()` returned `true` as soon as `autoAllows()` matched — before the dangerous-command "Safety Ceiling" and the PolicyEngine `REQUIRE_APPROVAL` check. `autoAllows()` had no knowledge of command content and returned `true` for `effect:'shell_outside'` (unsandboxed shell), so `rm -rf /` with `unsandboxed:true` ran with no prompt. Vega's audit (F1 Critical, F3 Medium) reproduced the bare-regex bypasses `rm -rf "/"`, `rm -rf '/'`, `X=/; rm -rf $X` and `rm -rf -- /`.

**Root Cause:** The `autoAllows()` early return was placed above the checks that were supposed to override it, so those checks were unreachable in auto mode. The effect table treated `shell_outside` as just another auto-able effect, contradicting the ratified design (`docs/design/external-engines.md` ~L250) that unsandboxed shell is a separate approval, never auto and never covered by "always". The `bash-validator.ts` denylist matched a bare `/` after `rm -rf` and did not normalize quoted paths or variable indirection.

**Rule:** Compute every must-prompt condition (dangerous pattern, PolicyEngine, persistent writes, `shell_outside`) *before* the `autoAllows()` early return and gate that return on `!mustPrompt`; make `autoAllows()` return `false` for `shell_outside` in every mode. In `bash-validator.ts`, strip quotes around root/home path arguments before matching and add a pattern for `rm -r/-f` on a bare `$X`/`${X}` target. Tests: `packages/shared/test/approval.test.ts` F1 case, `packages/desktop/test/ipc-bridge.test.ts` F1 case, `packages/local-exec-daemon/test/bash-validator.test.ts` F3 cases; each goes red when its fix is reverted. Treat the denylist as defense-in-depth only — the OS sandbox is the real boundary.
